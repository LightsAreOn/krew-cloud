Section 1 · Overview

How the KREW QMS works

Owner: QSM (Monica) · reviewed by CTO & CLO

The QMS is KREW''s single source of truth for every controlled document and record. It is built so that all our data lives in one database, under reference numbers with logic, with full version history — and every agent has instant access to all of it, always. This document explains how it works and how it is built.

What it is for

A governed company needs to know, at any moment: what documents exist, which version is live, who approved it, what changed, and where the file is. The QMS answers all of those from one place. Nothing is "official" until it is registered here — governance is operational, not aspirational.

Reference numbers — the logic

Every document has a stable reference number that never changes, of the form:

KREW - SERIES - NUMBER e.g. KREW-BOARD-004, KREW-OPS-009, KREW-LGL-005

The series groups by function, and the number is sequential within it:

SeriesHoldsSeriesHolds
BOARDBoard / strategyRSKRisk assessments
LGLLegal & contractsOPSOperations / SOPs / this doc
PRDProduct definitionsBRANDBrand & content standards
FINANCEFinancial recordsHRPeople records

The reference number is the anchor for everything: every version, every audit entry, and the stored file all hang off the same doc_id. Find the number, and you have the document''s entire life.

How it is built — three layers

LayerTableRole
Registerqms_documentsOne row per document — identity, owner, approver, the pointer to the live version.
Versionsqms_document_versionsOne row per (doc_id, version) — the content, text, file pointer, status, history. Never deleted.
Audit logqms_audit_logEvery event — who did what, when, and why.
One reference, many versions, full history. A document with five versions is five rows in the versions table under one doc_id. Old versions are never deleted — they are marked superseded. "Full history" is simply every row for that reference.

Section 2 · Versions & lifecycle

One document, its whole life

Owner: QSM (Monica)

The version record

Each version row carries everything about that version of the document:

FieldWhat it holds
doc_id + versionThe reference and the version string (1.0, 1.1, ...). Unique together.
statusWhere it is in the lifecycle (below).
title, author_agent, change_noteWhat it is, who wrote it, what changed.
content_textThe document''s plain text — what agents search.
storage_path / content_b64Pointer to the rendered file in Storage, or small files inline.
sha256, bytes_originalIntegrity checksum and size.
embeddingVector for semantic search (see Section 3).
approved_by, approved_atThe approval record.

The lifecycle

draft → in_review → approved → superseded → retired
  • draft — being written.
  • in_review — out for the team / approver to check.
  • approved — the live, official version. Only one per document at a time.
  • superseded — was approved, replaced by a newer approved version. Kept for history.
  • retired — no longer in use, but never deleted.

The rule the database enforces

When a version is set to approved, the system automatically (a) marks any previously approved version of that document as superseded, and (b) re-points the register at the new version. It is impossible to have two live versions of the same document. Approving is the single act that makes a version go live — separation of duties (who may approve) is enforced at the agent/role layer above, and every approval is written to the audit log.

Worked example, already live in the system: KREW-OPS-007 has version 1.1 marked superseded and version 1.2 as the current draft, both under the one reference — exactly this model, on real data.

Section 3 · Search, ingestion & access

How agents find anything, instantly

Owner: QSM (Monica) · CTO (Sheldon) for ingestion

Two ways agents search

  • Full-text search — exact words and phrases, via a full-text index on content_text. Live now.
  • Semantic search — meaning, not just words, via the embedding vector and a pgvector index. Switches on once embeddings are generated (below).

Ingestion — how a document enters and stays searchable

Every time a document version is created or updated, the agent OS runs this step so the document is immediately findable:

1
Render & store the file. The rendered file (HTML, xlsx, PDF) is uploaded to the Storage bucket at a path keyed by reference and version — SERIES/doc_id/version/filename — and storage_path is written to the version row. Small documents may also be stored inline (gzip+base64).
2
Extract the text. The document''s plain text is extracted and written to content_text. This is what powers full-text search and what agents read.
3
Embed. The text is sent to the embedding model and the resulting vector is written to embedding. This powers semantic search.
4
Checksum & log. The sha256 and size are recorded for integrity, and an entry is written to the audit log.

The same step runs for every new version, so search and history are always current. A change of foundation or embedding model triggers a re-embed sweep across all versions, so search quality never drifts.

Status today: full-text search is live (the business plan, KREW-BOARD-004, is already text-indexed and searchable). Embeddings are populated by step 3 once the embedder is wired; the vector column and index are ready. Confirm the embedder''s dimension before the first run.

Instant access for every agent

Because the register, every version, the full history, the text, and the file pointers all live in one database, any agent can in milliseconds: find a document by reference or by meaning, read its current text, see every prior version and what changed, and retrieve the exact file. There is no separate file store to reconcile and no "which copy is right?" — the QMS is the answer.

Is it manageable at size?

Yes. The searchable layer (register + text + metadata + embeddings) is small and fast and lives in the database; the heavy rendered bytes live in Storage, referenced by storage_path. This split means the database stays lean for query and backup while holding unlimited history. KREW has years of headroom before size is a consideration.

The rules every document follows

Governance principles

  • Nothing is official until registered — a document exists in the QMS sense only when it has a reference, an owner, an approver and a filed location.
  • One live version — enforced by the database; approving supersedes the prior version.
  • Separation of duties — the agent who drafts is not the agent who approves; approvals are logged.
  • Full auditability — every change is in the audit log and every version is retained. A billion-dollar story has to be auditable.
  • Confidentiality & retention — each record carries its classification and retention; confidential records sit under tight access control.
Why this matters. The QMS is what lets KREW run "no-hands-involved" without losing control. Agents do the work; the QMS makes that work findable, versioned, auditable, and trustworthy — quality and compliance built into the data model itself, not bolted on afterwards.
