Automated Processes Register

This document is the master register of every automated process running in the KREW infrastructure. It covers scheduled jobs (triggered by a timer) and event-driven functions (triggered by a user action or webhook). For every process it records: what it does in plain terms, when or how it triggers, what model or technology it uses, who owns it, what it reads, and what it produces.

This register must be updated every time a new automation is added, modified, or removed. Monica (QSM) owns the register. The CTO approves all changes.

Scheduled Automations — pg_cron

These processes run on a fixed timer using pg_cron, the PostgreSQL scheduling extension. All times are UTC. CEST (Norway summer) = UTC+2. The scheduler is always running inside Supabase and does not require any server to be manually started.

Boardroom Daily Snapshot
boardroom-daily-snapshot
02:15 UTC
04:15 CEST

Every day at 04:15 (Oslo time), all current boardroom discussions, projects, and cases are copied into a backup table. This creates a daily snapshot that can be used to recover data if anything is accidentally deleted or corrupted. No AI involved — pure database copy operation.

07
Boardroom 30-Day Data Purge
boardroom-30d-purge
02:45 UTC
04:45 CEST

Thirty minutes after the daily snapshot, old backup data is deleted. Any backup older than 30 days is removed. Soft-deleted discussions, projects, and cases (those marked deleted but still in the database) are also permanently removed if they have been in the deleted state for more than 30 days. This is the data retention policy in action — governed by QSM under GDPR Article 5(1)(e).

Workforce Monitoring
09
Agent Health Monitor
harm-owl-hourly
:07 every hour
07 * * * *

Every hour, seven minutes past the hour, an automated check runs across all KREW agents. It reviews agent run logs, checks for failures, monitors error rates, and flags any agent that is underperforming or has stopped running. This is the KREW equivalent of an HR health check — the Workforce Manager checking that everyone is working. Alerts post to the appropriate channels if thresholds are breached.

Adding a New Automation

When a new automated process is added, the following steps must be completed before it can go live: (1) Document it in this register with all fields completed. (2) Get CTO approval on the technical implementation. (3) Get QSM sign-off that the process is logged and monitorable. (4) Add a line to KREW-OPS-013 if it is part of the Brief Pipeline. (5) Bump this document's revision number and update the "Last updated" date.
